# Workflows

A workflow connects steps, people, tools, and approval points. It should make
handoffs clear without assigning unconsenting volunteers or turning a draft
into policy.

## Current material

- [Project steward](../skills/project-steward.md) — draft skill for preparing a
  project brief and proposing a small next step.
- [Media requests](../knowledge/media-request-workflow.md) — unapproved workflow
  covering minimal intake, private routing, review, and authorized responses.
- [Website work](../reference/website-workflow.md) — manual reference for an
  authorized content/code change, deferring to current website guidance.
- [Support-tool orchestration](../tools/orchestration.md) — reference pattern
  for moving from a bounded request to review and reusable knowledge.
- [Slack support pilot](../integrations/slack/README.md) — experimental
  conversational routing to a separately qualified restricted worker, or
  approval-first proposal intake. Neither automatically runs powerful workers.
- [Email reply alerts](email-reply-alerts.md) — proposed proactive notifications
  and draft replies in a restricted Slack channel, with manual sending or an
  explicitly approved-send design. No mailbox or sending connector is enabled.

These links point to one canonical copy of each resource. None creates a
schedule, sends a message, installs a skill, or grants publishing permission.
New workflows should identify inputs, outputs, human decisions, stop conditions,
and a way to check completion.
