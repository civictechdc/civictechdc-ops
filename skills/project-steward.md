# Project steward

**Status:** draft task procedure; not installed or organizationally approved.
**Reviewed:** November 3, 2026. **Maintaining role:** unassigned.
**Provenance:** proposed support workflow for this library, informed by its
[working principles](../knowledge/organizational-context.md); not evidence of
a decision or commitment by a project team.

## Use when

A human requests a project intake summary, preparation for a work session,
continuity note, or handoff. The goal is one useful, capacity-aware next step,
not supervising volunteers or taking over a project.

## Inputs

- The request, intended audience, scope, and deadline if any.
- Authorized sources and their dates, with current project/maintainer context
  confirmed where necessary.
- Known volunteer capacity, user involvement, and constraints. Mark unknowns
  rather than inventing people, availability, or demand.

## Procedure

1. Read the request and relevant current sources. Resolve important conflicts
   with a human rather than promoting old notes into current facts.
2. State the problem and intended users. Distinguish user evidence from
   assumptions and proposed solutions.
3. Use the [project brief](../templates/project-brief.md) to capture context,
   dependencies, and the smallest plausible next milestone.
4. Propose at most three small tasks using the
   [task brief](../templates/task-brief.md). Include useful nontechnical work
   when appropriate; do not assign people or assume a commitment.
5. Identify questions, privacy concerns, maintenance needs, and human decisions.
   Offer narrowing, pausing, or handing off when capacity is unclear.
6. Return a concise draft with sources/check dates, proposed next steps, and
   a clear request for review. Save only public-safe reusable knowledge here.

## Output and completion check

The result should let a human answer:

- What need and user evidence are we working from?
- What is the next bounded milestone, and how would we recognize completion?
- Which inputs or decisions remain unconfirmed?
- What capacity and maintenance expectations are explicit?
- Which actions, if any, still need approval?

Do not send messages, publish, change project status, open external tasks,
assign volunteers, merge code, alter service access, or make commitments solely
because this procedure suggests a next step. The exact action still needs an
authorized request and appropriate review.
